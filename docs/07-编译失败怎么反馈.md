# 07 · 编译失败了怎么反馈

代码量很大（40 多个 Swift 文件），第一次云端编译有可能出现编译错误。
用下面的方法把错误信息反馈给 AI，一般一轮就能修好。

---

## 一、去哪里找报错

1. 打开 GitHub 仓库 → **Actions** → 点进失败的那次运行（红色 ❌）
2. 点左侧 **构建 IPA** → 展开 **开始编译（禁用签名）** 这一步
3. 页面里找 **红色的 `error:` 行**（不是 `warning:`）
4. 从**第一个** `error:` 往上多看几行，往往前面会写"在哪个文件、哪一行"

示例：

```
/Users/runner/work/couple-app/couple-app/ios/Sources/Features/Chat/ChatView.swift:142:31: error: cannot find 'foo' in scope
```

这表示：文件 `ios/Sources/Features/Chat/ChatView.swift` 第 142 行、第 31 列，用了不存在的 `foo`。

---

## 二、反馈格式（直接复制这个模板）

```
【编译报错反馈】

1. Swift 语法检查任务：通过 / 失败
2. 报错文件与行号：
   ios/Sources/xxx/yyy.swift:142
3. 报错原文（把第一个 error 连同它前面 3 行一起复制）：
   ......
4. 一共有几个 error：（看日志里有几行 "error:"）
5. 我做了什么改动：（如果改过代码，说明改了哪里；没改就写"未改动"）
```

---

## 三、让反馈更省事的两个技巧

### 技巧 1：直接下载编译日志

工作流会在每次运行时上传日志，即使失败也能下载：

1. 失败的运行页面最下方 → **Artifacts** → 下载 `xcodebuild-logs`
2. 解压得到 `CoupleApp-xcodebuild.log`
3. 把这个文件（或其中包含 `error:` 的部分）发给 AI

### 技巧 2：只跑语法检查，1 分钟出结果

只想快速知道有没有低级语法错误时，可以让 AI 参考日志里的 **Swift 语法检查** 任务输出，
它比完整编译快得多（1 分钟左右），能提前发现括号、拼写、类型名之类的低级问题。

---

## 四、常见错误类型对照（自己也能判断）

| 报错关键字 | 含义 | 一般怎么修 |
| --- | --- | --- |
| `cannot find 'X' in scope` | 用了不存在的类型/变量 | 检查拼写，或补上定义 |
| `cannot convert value of type` | 类型不匹配 | 加显式转换或改参数类型 |
| `value of type 'X' has no member 'Y'` | 调用了不存在的属性/方法 | 检查名字，或看该类型是否真是这个 |
| `missing argument for parameter` | 调用参数没给全 | 补参数 |
| `extra argument` | 多给了参数 | 删多余的 |
| `ambiguous use of` | 有多个同名重载，编译器分不清 | 显式标注类型 |
| `escapes closure captures` / `self captured` | 闭包捕获问题 | 加 `[weak self]` 或 `self.` |
| `no such module 'X'` | 引用了不存在的模块 | 去掉该 import 或改用系统框架 |
| `type 'X' does not conform to protocol 'Codable'` | 结构体里有不能编码的字段 | 把该字段改成可编码类型 |
| `ambiguous expression type` / `unable to type-check this expression in reasonable time` | 视图表达式太复杂 | 把 `body` 拆成更小的子视图 |
| `@main attribute cannot be used` | 一个 target 里有多个 `@main` | 确认扩展的入口文件没被主 App 编译进去 |

## 五、真实案例（本项目首次云编译踩到的坑，供参考）

### 案例 1：XcodeGen 生成了 Xcode 16 的工程格式

```
xcodebuild: error: Unable to read project 'CoupleApp.xcodeproj'.
Reason: The project 'CoupleApp' cannot be opened because it is in a future Xcode project file format (77).
##[error]Process completed with exit code 74.
```

**原因**：XcodeGen 2.46+ 默认按 Xcode 16 格式（`objectVersion 77`）写工程文件，而 `macos-14` 跑的是 Xcode 15.4，读不了新格式。
**修法**：在 `ios/project.yml` 的 `options` 里显式加一行（已加好，别删）：

```yaml
options:
  projectFormat: xcode15_0   # objectVersion 60，Xcode 15 与 Xcode 16 都能打开
```

### 案例 2：并发闭包捕获了可变局部变量

```
Sources/.../LedgerAIService.swift:68:17: error: reference to captured var 'result' in concurrently-executing code
Sources/.../VaultView.swift:304:17: error: cannot assign to value: 'error' is immutable
```

**原因 1**：`await MainActor.run { ... }` 的闭包是 `@Sendable` 的，**不能引用 `var` 声明的局部变量**（只能引用 `let`）。
**修法**：进闭包前先转成 `let`：

```swift
let errorSnapshot = result.errorText          // ← 先转 let
await MainActor.run {
    self.isParsing = false
    if !errorSnapshot.isEmpty { self.errorText = errorSnapshot }
}
```

**原因 2**：`catch { }` 会自动绑定一个名叫 `error` 的常量，如果外面又写了 `var error: String?`，赋值就变成了给 catch 的 `error` 赋值（不可变）。
**修法**：换个变量名（例如 `failure`），不要在 `catch` 所在作用域里用 `var error`。

> 💡 加新功能时，只要写「`await MainActor.run { ... }` 里用到外面的变量」，就先把那个变量改成 `let`，能省掉一轮 8 分钟的云编译。

## 六、实在修不好怎么办

可以退一步，先只保证**能装上**：

```yaml
# .github/workflows/ios-build.yml 里可以先只构建轻量版
- name: 构建轻量版（无扩展）
  run: bash scripts/build-ipa.sh CoupleAppLite CoupleAppLite-unsigned
```

轻量版不包含小组件扩展，少一个 target，出错面更小。
先装上用起来，灵动岛之后再补。
